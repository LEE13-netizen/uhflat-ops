## 1. 목표와 완료 기준
1. 직원마다 **개인 아이디 + 6자리 PIN**으로 로그인한다. 자유 가입은 없다.
2. 업무 등록·처리 기록에 **로그인한 사람이 자동으로** 남는다(이름 입력칸 불필요).
3. 연속 실패 시 계정이 잠기고, **잠금을 우회할 수 없다**(서버 기준).
4. 신규 직원은 임시 PIN으로 첫 로그인 → 본인 PIN으로 바꾸기 전에는 다른 화면을 쓸 수 없다.
5. 권한 3단계(프로그램 관리자 / 부서 관리자 / 직원)가 **서버에서** 검사된다.
6. 관리자 계정은 2단계 인증(OTP 앱)을 거친다.
7. 직원 추가·PIN 초기화·잠금 해제·비활성화·부서 이동·권한 변경이 화면에서 되고, 모두 감사 로그에 남는다.
8. 퇴사자를 비활성화해도 그 사람이 남긴 업무 기록은 그대로다.
9. 기존 화면·메뉴·업무 흐름·데이터는 바뀌지 않는다.

## 2. 인증 방식 (핵심 결정)

### 2-1. 문제
- PIN 6자리는 경우의 수 100만 개라 잠금이 필수다.
- Supabase Auth에는 **계정별 잠금이 없다**(IP 단위 요청 제한만 있음).
- PIN을 그대로 Supabase 비밀번호로 쓰면, 누군가 우리 로그인 화면을 거치지 않고 Supabase 로그인 주소를 직접 호출해 잠금 없이 계속 시도할 수 있다.
- 지침: PIN을 그대로 저장하거나 **자체 검증 방식을 만들지 말 것**.

### 2-2. 추천: "서버 비밀값으로 감싼 PIN"
```
[로그인 화면] 아이디 + PIN
      │  (HTTPS)
      ▼
[서버 함수 login]  ← 비밀값 PEPPER는 여기에만 있음
  1) 아이디로 직원 찾기 · 비활성/잠금 확인
  2) 실제 비밀번호 = HMAC-SHA256(PEPPER, 사용자ID + ":" + PIN)  (44자, 사람이 모름)
  3) Supabase Auth에 그 비밀번호로 로그인 → 성공/실패
  4) 실패 횟수 기록 · 잠금 처리 · 감사 로그
      │
      ▼
[세션 발급] 이후는 일반 Supabase 로그인과 같음
```
- PIN 검증은 **Supabase Auth가** 한다(bcrypt 해시 저장·비교). 우리가 PIN 해시를 따로 만들지 않는다 → 지침 준수.
- Supabase Auth에 저장된 비밀번호는 PIN이 아니라 44자 값이라, PEPPER를 모르면 로그인 주소를 직접 두드려도 소용없다 → **잠금 우회 불가**.
- PEPPER는 서버 함수 비밀값(Supabase Edge Function secret)으로만 둔다. 코드·저장소·브라우저에 없다.
- 단점: PEPPER를 바꾸면 모든 직원 PIN을 다시 설정해야 한다 → 직원마다 `pepper_version`을 둬서 단계적으로 교체할 수 있게 한다.

### 2-3. 비교한 다른 방법
| 방법 | 장점 | 문제 |
|---|---|---|
| PIN = Supabase 비밀번호 그대로 | 가장 단순 | 직접 호출로 잠금 우회 가능 |
| 위 + Auth 훅으로 실패 횟수 차단 | Supabase 기능만 사용 | 해당 훅의 플랜 지원 여부 **확인 필요**(상위 플랜 전용일 수 있음) |
| PIN 해시를 우리 표에 저장해 직접 검증 | 잠금 확실 | 지침의 "자체 검증 금지"와 충돌 |
| **PEPPER로 감싼 PIN (추천)** | 잠금 확실 + 검증은 Supabase Auth | PEPPER 관리 필요 |

### 2-4. 잠금·세션 정책 (기본값, 조정 가능)
- 연속 5회 실패 → 15분 잠금. 24시간 안에 누적 10회 실패 → 부서 관리자가 풀 때까지 잠금.
- 실패 메시지는 "아이디 또는 PIN이 맞지 않습니다"로 통일(아이디 존재 여부 노출 안 함). 남은 시도 횟수는 3회 이하일 때만 표시.
- 금지 PIN: 같은 숫자 6개(000000), 연속(123456, 654321), 임시 PIN 그대로 재사용.
- 미사용 자동 로그아웃: 화면 조작이 없으면 **N분 후 PIN 화면으로**. 공용 기기면 짧게(예: 10분), 개인 휴대폰이면 길게(예: 8시간) → 기기 종류 확인 필요.
- 세션 토큰 수명 1시간, 자동 갱신. 비활성화된 직원은 다음 갱신 때 차단(서버 함수가 확인).

### 2-5. 관리자 2단계 인증
- Supabase MFA(TOTP, 무료)를 사용. Google Authenticator 등 OTP 앱으로 6자리 코드.
- 프로그램 관리자·부서 관리자는 첫 로그인 때 OTP 등록 필수, 이후 로그인마다 OTP 입력.
- 직원 관리·권한 변경 서버 함수는 **2단계 인증을 마친 세션(aal2)만** 허용.

## 3. 데이터 구조 (새 표)
모든 표에 `branch_id`(현재 `SEOCHO`)를 둔다. 다지점 화면은 만들지 않는다.

```
branches        지점      id 'SEOCHO', name 'UH FLAT 서초', mode 'SINGLE'
departments     부서      id, branch_id, code(FO·HK·FM·MG), name, en, active, sort
profiles        직원      user_id(=auth 사용자), branch_id, login_id(고유), name, title(직급),
                          dept_id, role(super_admin·dept_admin·staff), active,
                          must_change_pin, pepper_version, created_at/by, deactivated_at/by
auth_guard      잠금 상태  user_id, failed_count, window_started_at, locked_until, last_login_at
                          → 브라우저에서 읽기·쓰기 불가(서버 함수만)
audit_logs      감사 로그  id, branch_id, at, actor_id, action, target_type, target_id,
                          before(jsonb), after(jsonb) → 추가만 가능, 수정·삭제 불가
```
- 이름·부서·직급·권한을 따로 둔다(지침 12장). 부서 코드는 앱의 기존 부서 ID(FO·HK·FM·MG)를 그대로 써서 기존 기록과 호환한다.
- 로그인 아이디는 Supabase 내부적으로 `아이디@staff.uhc.internal` 형태의 계정이 된다(메일은 보내지 않음, 직원은 아이디만 앎).
- 직원 개인정보는 이름·직급·부서만. 전화번호·생년월일 등은 받지 않는다(최소 수집).

## 4. 권한
### 4-1. 역할
| 역할 | 할 수 있는 일 | 할 수 없는 일 |
|---|---|---|
| 프로그램 관리자(super_admin) | 모든 부서 화면, 부서 추가·수정, 모든 직원 관리, 권한 변경, 감사 로그 조회, 설정 | — |
| 부서 관리자(dept_admin) | 자기 부서 화면, **자기 부서** 직원 추가·PIN 초기화·잠금 해제·비활성화·직급 수정 | 다른 부서 직원 관리, 권한 올리기, 부서 이동 |
| 직원(staff) | 자기 부서 화면, 업무 등록·처리, 본인 PIN 변경 | 직원 관리 |

### 4-2. 서버 검사 (RLS + 서버 함수)
- `profiles`: 본인 행 읽기 가능. 같은 지점 직원의 **이름·부서·직급만** 읽기 가능(업무 기록에 이름을 보여 주기 위해). 쓰기는 서버 함수만.
- `departments`, `branches`: 같은 지점이면 읽기. 쓰기는 프로그램 관리자 서버 함수만.
- `audit_logs`: 프로그램 관리자만 읽기. 쓰기는 서버 함수만.
- `ops_docs`(기존 업무 데이터): **활성 직원 + 같은 지점**이면 읽기·쓰기(지금의 "부서 계정이면 전부"를 개인 계정 기준으로 바꿈).
  - ⚠ 부서별로 서로 못 고치게 하는 서버 제한은 업무가 JSON 문서로 묶여 있어 1단계에서 불가 → **2단계(업무 정식 표)에서 적용**. 1단계는 화면 제한 + 개인 기록(누가 바꿨는지 남음)으로 운영.

## 5. 서버 함수 (Supabase Edge Functions)
| 함수 | 하는 일 | 허용 |
|---|---|---|
| `login` | 아이디+PIN 확인, 잠금, 세션 발급, 첫 로그인 여부 반환 | 누구나(로그인 전) |
| `change-pin` | 현재 PIN 확인 후 새 PIN 설정, 금지 PIN 검사, `must_change_pin` 해제 | 본인 |
| `staff-admin` | 직원 추가(임시 PIN 생성·1회 표시), PIN 초기화, 잠금 해제, 비활성·재활성, 직급 수정, 부서 이동·권한 변경(프로그램 관리자만) | 관리자(aal2) + 부서 범위 검사 |
- 비밀 키(service_role)와 PEPPER는 함수 비밀값에만 있다.
- 모든 관리 동작은 `audit_logs`에 전·후 값으로 남는다.

## 6. 앱 연결 (기존 화면 최소 수정)
- 앱은 원래 로그인 사용자 창구(`UAPI`: 내 ID·내 이름·여러 사람 이름 조회)를 지원한다. 웹판에서 이 창구를 `profiles`로 채운다.
  - 효과: 업무·청소·불출 기록에 **사용자 ID가 자동 저장**되고, 화면에는 그 사람 이름이 나온다. 이름 입력칸은 "로그인: 홍길동(키핑)" 표시로 바뀐다.
- 부서 고정은 지금의 `[web]` 코드를 그대로 쓰되, 허용 부서를 `profiles`에서 읽는다(프로그램 관리자 = 모든 부서).
- 기존 기록(이름만 있고 ID 없음)은 그대로 이름으로 표시된다.

## 7. 화면
기존 디자인(색·글꼴·버튼·카드)을 그대로 쓴다.
1. **로그인**: 아이디 입력 → PIN 6자리 숫자판(지금의 큰 숫자 버튼 재사용). 잠금 시 "15분 뒤 다시 시도하거나 부서 관리자에게 요청하십시오".
2. **첫 로그인 PIN 변경**: 새 PIN 두 번 입력, 금지 PIN 안내. 끝나기 전에는 다른 화면으로 못 감.
3. **관리자 OTP**: 첫 등록 시 QR 코드, 이후 6자리 입력.
4. **내 정보**(머리 메뉴): 이름·부서·직급, PIN 변경, 로그아웃(=지금의 "잠금").
5. **직원 관리**(설정 탭의 기존 "직원 명단"을 확장): 목록(이름·아이디·부서·직급·권한·상태·마지막 로그인·잠금 여부), 추가, PIN 초기화, 잠금 해제, 비활성화. 부서 관리자는 자기 부서만 보임.
6. **감사 로그**(프로그램 관리자, 이력 탭 안): 누가 언제 어떤 직원·권한을 바꿨는지.
- 각 화면에 짧은 안내 문구(지침 15장 업무 가이드): 예) 직원 추가 화면에 "임시 PIN은 한 번만 보입니다. 직원에게 직접 전달하고, 첫 로그인 때 바꾸게 됩니다."

## 8. 전환 계획 (운영 중단 없이)
1. 시험 환경(두 번째 Supabase 프로젝트 또는 브랜치)에서 전부 구현·시험.
2. 운영 DB 백업 → 새 표·함수 추가(기존 `ops_docs`·데이터는 그대로).
3. 프로그램 관리자 계정 생성(본인) → 부서별 직원 계정 생성, 임시 PIN 배부.
4. **병행 기간**(예: 1~2주): 개인 로그인과 기존 부서 PIN 둘 다 가능. 로그인 화면에 "개인 계정으로 로그인해 주세요" 안내.
5. 전 직원 개인 계정 사용 확인 → 부서 공용 계정 5개 비활성화(승인 항목 B).
6. 되돌리기: 새 표·함수를 끄고 이전 로그인 코드(태그로 보관)로 배포하면 즉시 복귀. 업무 데이터는 그대로라 손실 없음.

## 9. 시험 항목 (완료 판정)
- 로그인 성공·실패, 5회 실패 잠금, 15분 후 해제, 누적 10회 잠금 → 관리자 해제
- Supabase 로그인 주소를 직접 호출해 PIN 대입 → 실패(우회 불가) 확인
- 첫 로그인 PIN 변경 강제, 금지 PIN 거부
- 자동 로그아웃, 비활성 직원 차단(이미 로그인된 기기 포함)
- 부서 관리자가 다른 부서 직원 관리 시도 → 서버 거부
- 직원이 `profiles`·`audit_logs`를 직접 고치거나 읽기 시도 → 서버 거부
- OTP 미완료 관리자 세션의 직원 관리 → 서버 거부
- 업무 등록 시 사용자 ID·이름 자동 기록, 기존 기록 표시 정상
- 기존 기능(현황판·청소·불출·할 일·이력·통계·설정) 회귀 시험, PC·휴대폰

## 10. 비용
- Edge Functions(무료 월 50만 회), MFA(TOTP), Auth 모두 무료 플랜 범위. 추가 비용 없음(수치는 가격표 재확인).
