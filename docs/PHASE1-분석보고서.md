# UHC OPERATION SYSTEM — 최초 분석 보고 (PHASE 1~3)

작성일 2026-11-26 · 대상: UH FLAT OPS(아티팩트 v0.19 + 웹판) · 코드·DB 변경 없음

## 1. 현재 시스템의 객관적인 상태

| 항목 | 현재 |
|---|---|
| 개발 원본 | claude.ai 아티팩트 "통합 업무 시스템" v0.19 |
| 기술 | 순수 JS(빌드 도구·프레임워크 없음), 파일 14개 약 280KB. 화면은 `app.js` 한 파일(160KB)이 문자열 템플릿으로 다시 그림 |
| 웹판 | GitHub Pages(공개 저장소) + Supabase(도쿄, 무료). `sync.ps1`이 아티팩트 + 웹 전용 파일을 합쳐 배포 |
| 데이터 | `ops_docs` 표 하나에 JSON 문서로 저장(모음 18개 정의, 8개 사용). **실제 운영 데이터 있음**: 업무 4, 처리 이력 7, 청소 3, 객실 기준 1 등. DB 11MB |
| 실시간 | Supabase Realtime(다른 기기 변경 2초 내 반영 확인) |
| 인증 | 부서 공용 계정 5개(4자리 PIN → Supabase Auth 비밀번호). 개인 식별 없음, 작성자 이름은 입력칸에 자유 기재 |
| 서버 권한 | "부서 계정이면 모든 문서 읽기·쓰기". 부서 구분은 화면에서만 |
| 파일 저장 | Storage 버킷 없음. 분실물에 "사진 있음" 체크만 |
| 예약표 처리 | 예약표·청소표(xlsx) 업로드 → 날짜·객실별 상태만 저장. 이름·연락처·예약번호는 저장하지 않도록 설계됨 |

기존 기능: 현황판(층별 객실 칸·숙박 상태·부서별 업무 표시·긴급/미확인), 청소·재실(프론트→키핑 흐름, 퇴실완 시 비번 변경 업무 자동 생성), 불출·분실물·수건 재고, 할 일(업무 7종·상태 7단계·우선순위 3단계·다른 부서 요청은 요청 부서 확인 후 종결), 이슈 목록(객실별), 이력(등록·상태·수정 전후·댓글), 통계(관리자: 입실 준비·부서 부하·장기 미처리·응답 시간·반복 객실/분류), 설정(객실 등록, 예약표·청소표 업로드, 직원 명단, 전체 백업 내보내기), 영문 화면·야간 모드·글자 크게. 교대·인수인계(3단계)와 체크리스트(4단계)는 "준비 중".

## 2. 강점 (지침과 이미 맞는 부분)
- **객실 중심 현황판**(지침 4)이 이미 핵심 화면이고, 객실별 미해결 업무 수·긴급 표시가 있음
- **부서 간 흐름 + 요청 부서 최종 확인**(지침 7): 시설 완료 → "완료 대기" → 프론트 확인 → 종결이 엔진에 구현됨
- **변경 이력**(지침 5·6): 상태 이동, 항목별 수정 전·후 값, 댓글이 `taskEvents`에 남음
- **민감정보 자동 가림**: 카드번호·객실 비밀번호·도어 코드를 저장 전 가림
- **반복 이슈 통계**(지침 10) 기초 존재
- **확장 여지**: 모든 데이터에 `propertyId`(지점 개념)가 이미 있음. 저장 창구가 `OPS.Store` 하나라 백엔드 교체가 쉬움
- **동시 수정에 강한 단위**: 청소는 "날짜__객실" 한 문서, 불출은 요청 1건 = 1문서

## 3. 개선이 필요한 문제점
1. **개발 원본이 아티팩트**: 개인 로그인·파일 저장·서버 권한은 아티팩트 안에서 만들거나 시험할 수 없음. 지침 4~7단계를 하려면 원본을 GitHub 코드로 옮겨야 함
2. **공용 부서 계정**: 등록자·처리자 개인 기록 불가(지침 5·11·12의 전제와 충돌)
3. **권한이 화면에만 있음**: 키핑 계정도 DB상으로는 모든 업무를 고칠 수 있음(지침 11 위반)
4. **JSON 문서 한 표**: 필드 단위 권한·검색·통계 SQL이 어렵고, 수정이 "마지막 저장 우선"이라 같은 업무를 두 사람이 동시에 고치면 덮어쓸 수 있음. 이슈 번호 자동 채번 없음
5. **큰 단일 파일**(app.js 160KB)·자동 테스트 없음 → 변경 시 회귀 위험
6. **공개 저장소**: 무료 GitHub Pages 조건 때문. 지침의 비공개 저장소와 불일치, 코드에 개인 연락처 포함
7. **백업**: 수동 내보내기만 있음. Supabase 무료 플랜은 자동 백업이 없는 것으로 알고 있음(확인 필요)

## 4. 기술적 위험 및 제약
- **6자리 PIN**: 경우의 수 100만. Supabase Auth 기본 방어는 IP 단위 요청 제한뿐이고 계정별 잠금이 없음 → 로그인을 서버 함수(Edge Function)로 받아 실패 횟수를 기록·잠금해야 함. 관리자 2단계 인증은 Supabase MFA(TOTP)로 가능
- **동영상**: 무료 Storage 1GB·파일당 50MB 한도(확인 필요) → 짧은 영상만, 업로드 전 길이·용량 제한 필요
- **HEIC·MOV 미리보기**: 일부 브라우저(안드로이드 크롬의 HEIC 등)에서 미리보기 불가 → 가능한 경우 JPEG 변환, 안 되면 "미리보기 없음"으로 업로드
- **예약번호 기반 중복 방지**(지침 17-5): 현재는 개인정보 때문에 예약번호를 저장하지 않음. 날짜·객실 단위 덮어쓰기(중복 없음)는 이미 됨. 예약번호 단위로 신규·수정·취소를 구분하려면 예약번호 저장 결정 필요
- **운영 중 전환**: 실제 데이터가 쌓이기 시작함 → 구조 변경 전 백업·이관 스크립트·되돌리기 계획 필수
- **무료 플랜 일시 중지**: 7일 사용이 없으면 프로젝트가 멈추는 정책(확인 필요)

## 5. 권장 데이터베이스 및 시스템 구조
**원칙: 화면·업무 흐름은 그대로, 바닥(저장·권한)만 교체. 전면 재작성 안 함.**

- **프런트**: 현재 순수 JS 유지. 원본을 GitHub로 옮긴 뒤 필요한 부분만 파일 분리
- **호스팅**: Cloudflare Pages 또는 Vercel(비공개 저장소에서 무료 배포) → GitHub Pages 대체
- **DB: 하이브리드**
  - 권한·검색·이력이 중요한 것만 정규 표로:
    `branches`, `departments`, `profiles`(계정↔직원, 지점·부서·역할·직급·활성·첫 로그인 PIN 변경 필요), `rooms`, `tasks`(이슈 포함), `task_events`(상태·담당 변경·댓글·첨부 이력, 추가만 가능), `attachments`, `handovers`, `notifications`(또는 읽음 기록), `audit_logs`
  - 나머지 화면 상태(날짜별 객실 상태, 청소 진행, 수건 재고, 설정 등)는 `ops_docs` 유지 + `branch_id` 추가
  - **이슈는 별도 표 대신 `tasks` 확장**: `is_issue`, `issue_no`(자동 채번), `severity`(P1~P4), 보류 사유·재처리 예정일 → 업무→이슈 전환 시 번호·이력이 그대로 이어지고 중복 저장이 없음
  - 화면 코드는 그대로 두고, `OPS.Store`가 tasks·taskEvents 모음만 새 표로 연결
- **인증**: 개인 아이디(예: `hong.gd`) → 내부용 계정 이메일로 변환, 6자리 PIN = Supabase Auth 비밀번호(bcrypt 해시). 로그인·계정 생성·PIN 초기화는 서버 함수(비밀 키는 서버에만). 실패 5회 → 15분 잠금, 첫 로그인 PIN 변경, 일정 시간 미사용 시 자동 로그아웃, 관리자 MFA
- **권한(RLS)**: `profiles`에서 내 지점·부서·역할을 읽는 함수로 표마다 검사. 예) 업무는 같은 지점 + (내 부서가 요청/담당 부서이거나 관리자)
- **파일**: 비공개 버킷, 경로 `지점/업무ID/파일`, Storage 권한도 `attachments` 표 기준, 짧은 만료 Signed URL
- **데이터 입력**: 예약표 해석 모듈을 "공통 처리 모듈"로 분리 → 수동 업로드와 향후 Sheets API(서버 함수)가 같은 함수 사용

## 6. 단계별 개발 우선순위 (지침 PHASE 5 순서를 일부 조정)
0. **안전장치**: 현재 운영 데이터 백업, 저장소 비공개 + 호스팅 이전, 개발 원본 결정, 시험용 환경(두 번째 Supabase 프로젝트 또는 브랜치)
1. **개인 계정·권한**: 지점·부서·직원 표, 서버 로그인(잠금), 첫 로그인 PIN 변경, 관리자 MFA, 직원 관리(기존 설정 탭 직원 명단을 확장)
2. **업무·이슈 이전**: 정규 표 + 서버 권한 + 이슈 번호·P1~P4 + 기존 데이터 이관 + 감사 로그
3. **사진 첨부**(모바일 촬영·갤러리, 압축) → 다음에 동영상
4. **인수인계**(기존 "준비 중" 자리) + 필요한 알림만
5. **업무 가이드**: 업무 종류별 절차·확인 사항 카드를 등록 화면 옆에, 관리자가 수정
6. **검색·통계 확장**
7. **데이터 입력 공통 모듈 정리 + Sheets API 연결 준비**(실제 연결 전엔 "연결 대기"로만 표시)

각 단계: 시험 환경에서 확인 → 사용자 검토 → 운영 반영.

## 8. 사용자 승인이 필요한 변경 사항
- **A. 개발 원본 전환**: 지금은 "아티팩트에서 개발 → 웹 동기화". 지침 범위(개인 로그인·파일·서버 권한)를 하려면 **GitHub 코드가 원본**이 되어야 함. 아티팩트는 화면 시안 실험용으로만 쓰는 것을 권장
- **B. 부서 공용 PIN 폐지 시점**: 개인 계정 개통 후 4자리 부서 계정 종료
- **C. 호스팅 이전 + 저장소 비공개**: 웹 주소가 바뀜
- **D. 하이브리드 DB**(전면 정규화 대신)
- **E. 이슈 = tasks 확장**(별도 issues 표 대신)
- **F. 우선순위 매핑**: 긴급→P1, 주의→P2, 일반→P3, P4 신설
- **G. 예약번호 저장 여부**: 지침 17의 예약번호 기반 중복·수정·취소 구분에 필요. 현재는 개인정보 최소화로 저장 안 함
- **H. Supabase Pro 전환 시점**

## 9. 가장 먼저 진행해야 할 작업
1. 현재 운영 데이터 백업(전체 내보내기 + DB 덤프)
2. A·C 결정 → 저장소 비공개 전환과 호스팅 이전
3. 1단계(개인 계정·권한) 상세 설계서(표·권한 규칙·화면) 작성 → 검토 후 구현

## 확인 필요 항목 (추측으로 확정하지 않음)
- 부서별 실제 직원 수, 부서장(부서 관리자) 명단, 직급 체계
- 업무에 쓰는 기기: 개인 휴대폰인지, 공용 태블릿·PC인지(자동 로그아웃 시간과 잠금 정책이 달라짐)
- 현재 인수인계 방식(톡방·노트·엑셀 등)과 양식
- 업무 가이드 원문: `UH FLAT SEOCHO 자료/서초점 교육 자료.xlsx`(프론트 업무·결제·분실물·체크인·컴플레인·오버부킹 등 31개 시트)가 표준 절차의 1차 원천으로 적합해 보임 — 내용 검토 필요
- Supabase 무료/Pro 최신 한도, Auth 훅(로그인 시도 제한) 사용 가능 플랜
- 사진·동영상 보존 기간과 삭제 권한 정책
