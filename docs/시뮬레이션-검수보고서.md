# 하루 운영 시뮬레이션 검수 보고서 (2026-11-26)

실제 엔진(`js/svc.js`, `js/desk.js`, `js/core.js`)을 그대로 불러 가상 시계로 하루를 돌렸다.
화면(DOM)은 돌리지 않았다. 도구: `tools/sim/ops-day-sim.js` (`node tools/sim/ops-day-sim.js shared|assigned 시드`).

## 3. 문제점 (심각도 순)

### 높음
1. **룸메이드 배정이 없다.** 키핑 화면은 동 전체가 한 목록이고 "누가 이 방을 하는지"가 없다.
   - 재실 객실은 "청소 시작" 단계조차 없어 다른 사람이 하고 있는지 화면으로 알 수 없다.
   - 공유 목록에서는 재실 청소의 80~90%가 손님이 고른 시간을 넘겼다. 배정만 해도 약 40%로 줄었다.
   - 필요: 층·객실 단위 담당자 배정(인스펙터·부서장이 아침에), "내 방" 보기, 재실에도 "청소 시작".
2. **수리 중인 방이 입실 가능으로 넘어간다.** 퇴실 청소 중 결함을 시설 업무로 올려도 점검 완료(입실 가능)를 막거나 경고하지 않는다.
   - 시뮬레이션에서 결함 객실 대부분이 수리 전에 입실 가능 처리됐다.
   - 당일 입실이 만실이면 고장 객실에 손님이 배정될 수 있다.
   - 필요: 같은 객실에 열린 수리 업무가 있으면 입실 가능 버튼에 경고·확인, 현황판에 "수리 중" 표시.
3. **재실 청소는 "요청한 방만" 한다.** 재실 139실을 전부 프론트가 손으로 입력했다(약 93분, 07~11시 체크아웃 몰림과 겹침).
   - 요청을 못 받은 방은 청소되지 않는다.
   - "재실은 기본 정비" 정책이면 지금 구조는 일을 늘린다.
   - 필요: 지점 설정 "재실 기본 = 정비(거절만 입력)" / "요청 받은 방만" 선택. 여러 방을 한꺼번에 입력하는 기능.

### 중간
4. **점검(인스펙터)이 병목이다.** 인스펙터 3명일 때 점검 대기 90%가 공유 방식 51~86분, 배정 방식 25~44분이다. 15시 입실 맞추기를 좌우한다.
   - 화면에 "점검 대기"가 몇 분째인지, 동별로 몇 실 쌓였는지가 없다.
   - 필요: 점검 대기 시간 표시·정렬, 15시까지 남은 방 수 대비 예상 완료 경고.
5. **덮어쓰기(동시 수정) 위험이 구조적으로 있다.** 객실 청소 기록은 "내 화면에 있는 문서 + 바꾼 칸"을 통째로 저장한다(`OPS.Svc` → `Store.set`).
   - 늦게 도착한 다른 사람의 저장 알림이 내 화면의 최신 상태를 덮은 뒤 내가 저장하면, 그 사이 기록이 사라진다.
   - 이번에는 "키핑 확인"만 하루 2~9건 사라졌다. 그러면 깜빡임이 다시 생기고 확인 이력이 빠진다.
   - 퇴실 완료·우선 준비도 같은 구조라 와이파이가 나쁜 날엔 생길 수 있다.
   - 불출·업무는 서버에서 칸을 합치는 방식(`ops_patch`)이라 이번에 사라진 것이 없다.
   - 필요: 객실 청소 기록도 `Store.update`(서버 병합)로 바꾸고, 기록(log)은 서버에서 덧붙이기.
6. **"키핑 확인"이 공용이다.** 한 명이 확인을 누르면 25명 모두의 깜빡임이 꺼진다. 배정이 없으면 정작 그 방을 맡은 사람이 못 볼 수 있다.
   - 반대로 공유 목록에서는 동 전체 새 요청이 모든 휴대폰에서 깜빡인다(알림 피로).
   - 배정이 생기면 "담당자 확인"으로 바꿔야 한다.
7. **불출 "가는 중"에 잠금이 없다.** 두 사람이 거의 동시에 누르면 둘 다 간다. 하루 1~5건으로 적지만, 하우스맨이 늘거나 룸메이드도 불출을 잡으면 늘어난다.
   - 필요: 이미 누가 잡았으면 "○○ 가는 중" 확인 후 진행.

### 낮음·확인 필요
8. **실시간 알림량**: 하루 약 3.5만, 월 약 100만 건(이 모의에 들어간 모음만 센 값). 프론트 PC 탭 여러 개, 다른 모음까지 더하면 늘어난다.
   - Supabase 무료 플랜의 월 실시간 메시지 한도(알고 있는 값 200만 건)와 비교해 여유가 크지 않다. 공식 가격표로 확인 필요.
   - 운영 투입 시 Pro 전환 검토와 같은 시점.
9. **기기당 알림은 분당 최대 10~11건**이다. 알림마다 화면 전체를 다시 그리므로 저가 안드로이드에서 버벅임·배터리 소모를 실기기로 확인해야 한다.
10. **15시까지 못 맞춘 7~10실** 대부분은 레이트 체크아웃(13실)과 10~11시 퇴실 몰림 때문이다. 시스템 문제라기보다 운영 판단(레이트 승인 기준)이지만, 화면에 "15시 입실인데 아직 퇴실 전" 경고가 없다.

## 4. 좋은 점
- 하루 약 1,100번 저장, 34대 동시 사용에서 엔진 오류 0.
- 객실·날짜마다 문서 하나라 서로 다른 방끼리는 충돌이 없다. 불출·업무는 서버 병합이라 기록이 사라지지 않았다.
- 우선 준비(이른 입실)가 키핑 목록 맨 위로 올라가 12실 중 7~10실을 맞췄다.
- 키핑이 직접 퇴실 확인 → 프론트에 알림, "손님 아직 있음" → 프론트가 레이트·연장으로 답하는 고리가 끊기지 않고 돌았다.
- 불출이 요청 한 건 = 문서 한 건이라 "어느 방 끝났나요?" 되묻기가 없다. 대기 평균 16~19분.
- 기기 한 대가 받는 알림 양(분당 10건 안팎)은 실시간 화면으로 감당할 수준이다.

## 5. 필요한 것 (우선순위)
1. 룸메이드 객실 배정 + "내 방" 보기 + 재실 청소 시작 단계 — 효과가 가장 크다(재실 지연 80~90% → 약 40%, 헛걸음 없음).
2. 열린 수리 업무가 있는 객실의 입실 가능 경고(또는 차단) + 현황판 "수리 중".
3. 재실 기본 정책 설정(기본 정비 / 요청한 방만) + 재실 요청 일괄 입력.
4. 객실 청소 기록 저장을 서버 병합 방식으로(덮어쓰기 제거).
5. 점검 대기 시간 표시, 15시 입실 대비 남은 방 경고.
6. 불출 "가는 중" 중복 확인, 키핑 확인을 담당자 기준으로.
7. 실기기 점검: 저가 안드로이드 20대 수준에서 실시간 갱신 시 화면 버벅임.

## 6. 한계
- 화면은 돌리지 않았다. 버튼을 찾는 시간, 잘못 누름, 화면 다시 그리기 비용은 숫자에 없다.
- 작업 시간·결함률·요청 비율은 가정값이다. 서초 청소표·톡방 실제 값으로 바꾸면 더 정확하다.
- 야간(18시 이후) 불출·입실 응대, 객실 이동, 분실물, 컴플레인 이슈는 넣지 않았다.
- 프론트 업무 시간은 이 시스템에 입력하는 시간만 셌다. 전화·체크인 응대는 빠져 있다.
